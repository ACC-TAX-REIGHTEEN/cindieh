# PDF download emission is one module with split item sourcing

The four DOWNLOAD_PDF_ITEM emission sites (fetch interceptor, XHR interceptor, bulk e-faktur, bulk withholding) were collapsed into `scraper-pdf.ts` (`createPdfDownloadSession` + pure `unwrapPdfData`/`resolveInvoiceRow`/`buildPdfDownloadMessage`), with the fetch/XHR monkey-patches kept as thin adapters (they moved to `scraper-install.ts` with ADR-0038; `scraper.ts` is now the adapter that hands the page over as one injected environment).

The load-bearing part: **item sourcing is deliberately split and must never be unified.** Native downloads (interceptors) resolve the invoice row from the grid-capture map (`invoiceRowMap`) because the download response carries only base64; bulk downloads already hold the full row and must pass it through untouched. A previous bug produced `TANPA_REFERENSI` filenames when the two paths were conflated — do not "simplify" them back together.

The second load-bearing part: **the native-download XHR response handling is a two-call contract, and the listener must be wired at `open()`.** `wireNativeDownloadXhrListener` (`scraper-pdf.ts`) is called from the `open()` patch — before the portal registers its own response reader (it does after `open()`, before `send()`), and listener registration order is callback order. It acts on `readystatechange` at readyState 4, which fires *before* the `load` event, so the sabotage precedes the portal's reader whichever event it listens on. The listener stays inert until `send()` arms the XHR via `prepareNativeDownloadXhr` (native, string body, non-bulk via `__isCindiehBulk`), which sets `__downloadArmed` and stashes `__downloadBody` for row resolution. On interception, both `responseText` and `response` accessors are rewritten to a failure payload (`IsSuccessful: false`, empty `Content`) so the portal takes its error branch and writes no file of its own. The dummy MUST stay a failure: the portal runs its save routine on every successful response, so an earlier success-with-empty-Content dummy made it save a 0-byte PDF with the Coretax name.

Both halves are load-bearing and their failures look different: wiring inside `send()` (the original bug) runs our sabotage *after* the portal's reader — the portal downloads its own PDF, so the user gets two files. A success-shaped dummy (a regression caught on the live portal) leaves `IsSuccessful` true, so the portal saves an *empty* Coretax-named PDF alongside ours. A missing arm call (another regression caught on the live portal) leaves the listener pass-through forever — no `DOWNLOAD_PDF_ITEM` emission at all, so only the native file downloads. Do not move the wiring into `send()`, do not make the dummy a success payload, and do not drop the arm call for "simplicity".

The sabotage is the PRIMARY block (confirmed on the live portal); the monkey-patch guards behind the processing flag are only backup nets for the corridors where the portal would save a PDF if the sabotage ever failed (defineProperty refusal, unparseable response, unexpected event order). Only two targeted nets are kept, one per save corridor: `HTMLAnchorElement.click` (anchor carries `download` or a `blob:` href) and `window.open` (`blob:` URLs only). `URL.createObjectURL` is deliberately NOT patched and must stay unpatched: it sits on the same corridor as the anchor net (blocking either link of the Blob → createObjectURL → click chain stops the save) and, unlike the other nets, never self-resets — it silently blocked every legitimate PDF blob on the page for the whole 5s processing window. The retained nets self-reset via `clearProcessing` when tripped, so one intercepted save never suppresses later legitimate downloads.

Two audit follow-ups (2026-09-18) hardened the same paths. The fetch interceptor's body now lives in `scraper-fetch.ts` (scraper.ts keeps the adapter) so its **issue-the-request-exactly-once** contract has regression coverage: a parse/emit failure *after* the response arrived hands the real response back instead of replaying the request, which had hit the download endpoint twice and let an un-sabotaged response reach the portal. And `handleNativeDownloadXhrLoad` disarms the per-XHR arm state *before* handling, so a duplicate readyState-4 fire or a reused XHR can never re-handle one download with a stale request body — `send()` re-arms for the next request. A third follow-up moved the two **backup** nets against a duplicate native save (anchor clicks and `window.open`) out of the scraper.ts IIFE into `scraper-nets.ts`: injected targets make their block / pass-through / self-reset behaviour testable, and their single `restore()` now owns the teardown of both corridors. The response sabotage stays the primary block; these nets only cover the save corridors it would leave open. The last extraction moved the three XHR prototype patches themselves into `scraper-xhr-patches.ts`, so the open()-time listener ordering (the fix for the duplicate-download bug) and the filter-injection / grid-capture behaviour are now pinned by their own suite instead of only by the wiring in the IIFE. A final follow-up covers that wiring: `scraper-boot.unit.test.ts` imports the real `scraper.ts` over a fake DOM and asserts that all six surfaces change reference on install and are all restored on `pagehide`, and that a single refused restore cannot strand the rest. Extraction alone would have left "did the adapter hand the factory the right prototype?" untested — the seam suites cannot see it.

Status: accepted.
