# AGENTS.md

## Project

**Cindieh** — a Manifest V3 browser extension (Chrome + Firefox) for the Indonesian DJP Coretax tax portal (`coretaxdjp.pajak.go.id`). It replaces slow portal workflows with one-click features: bulk export of grid data to Excel/CSV, bulk PDF downloads, reference-number search, a comparer that checks internal invoice records (pasted from Excel) against Coretax, and an accuracy checker (Pengecekan) that recomputes each recorded PPN Keluaran row's DPP / DPP Nilai Lain / PPN against a chosen benchmark (Acuan).

Tech: TypeScript (strict), esbuild bundling, SheetJS (`xlsx`), vanilla DOM/CSS — no UI framework. Commands and scripts live in `package.json`; install deps with `pnpm install`.

**Language split:** user-facing strings (UI text, alerts, panel status) and the README are in **Indonesian**; code comments and this file are in English. Keep user-visible text in Indonesian.

**Architecture decisions** live in `docs/adr/` (numbered, one per decision; see `docs/adr/README.md` for the index). The domain glossary is `CONTEXT.md`. When changing the shape of a module, check both before re-litigating a settled seam.

## Two-worlds architecture

The extension runs in two JavaScript worlds on the Coretax page that communicate **only** through token-validated `postMessage`:

- **Isolated world** — `src/content/main.ts`: the content script (has `browser.runtime`). Injects in-page UI, fires browser downloads, relays messages. Workflow UI lives in-page; the manifest also declares an action popup (`popup/popup.html`) that owns every stored preference — master switch, export mode, default file format, filename prefix, pacing, bulk-download confirmation, comparer defaults, debug switch, completion notifications — via `storage.local`, which is its only channel (see Gotchas).
- **MAIN world** — `src/content/scraper.ts`: injected into the page via a `<script>` tag pointing at the web-accessible `content/scraper.js`. It sits next to the portal's own code, so it can intercept XHR/fetch, read request bodies (filters), and **capture** API responses for scraping and PDF download. It has no browser API.

The **bridge token** correlates messages with the current bridge: `bridge.ts` generates it in the isolated world and passes it through the script URL without storing it on `window`. MAIN-world code can still observe it through the shared DOM and `postMessage` traffic; it is not secret authentication against hostile same-page scripts. `shouldProcessPageMessage` checks source, origin, token, and direction. Source/origin bind the window and origin, not the JavaScript world; `FROM_PAGE` and `FROM_CONTENT` are protocol fields, not proof of sender identity. Keep the two-worlds seam and token validation with these accepted limitations (ADR-0007).

Key message types:
- isolated → MAIN: `START_SCRAPE` (carries `skipPdf` when the request is an XLSX/CSV export rather than a bulk PDF download — see `scrapeIntentForFormat`, and `batchMonths` to sweep a whole tax year as ONE Run — see `scrape-batch.ts`/ADR-0018), `STOP_SCRAPE`, `SCRAPE_BY_INVOICES`, `SET_SERVER_FILTER`, `RESET_SCRAPER`, `START_PDF_DOWNLOAD`
- MAIN → isolated: `INJECTED_READY`, `SCRAPE_PROGRESS`, `SCRAPE_COMPLETE`, `SCRAPE_ERROR`, `DOWNLOAD_PDF_ITEM`, `SCRAPE_DATA_CHUNK` (one slice of a result too large to clone in one message; the completion's `dataChunks` names how many must arrive, and an incomplete transfer is reported rather than settled — ADR-0017)

`main.ts` and `scraper.ts` each run one `createMessageDispatcher` (from `postmessage-guard.ts`) — a guard-then-dispatch seam per world, keyed by message `type`. New message types register in the handler table of the world that receives them. Run state lives in `run-lifecycle.ts` so the in-page panel survives content-script restarts and SPA navigation. A **Run** spans both worlds (CONTEXT.md): the bridge gives it a `runId`, the Scraper owns its cancellation and identity (ADR-0010), and `run-lifecycle.ts` owns its outcome and debts (ADR-0014). The two halves share no code.

## Conventions

Existing code follows these patterns — new code should match them:

- **Testability first:** logic extracted from the world-entry scripts is written as pure functions with browser/DOM dependencies injected through context interfaces (`ActionDeps`, `ScraperContext`, `InterceptContext`). Add new flows the same way instead of growing `scraper.ts`/`main.ts`. State that outlives one call belongs in a module with a `createX()` factory and an exported singleton, not in a caller.
- **The world-entry wiring is itself tested.** The popup's own context is the smallest instance: every control is looked up defensively (`byId` returning null is a supported state), so the popup still opens when storage or the markup misbehaves.
- **A feature that only one page can use belongs in that page's menu, not in the toolbar.** The year-wide export adds one item to the export dropdown, built only on PPN Keluaran (`isOutputTaxPage()`), because a toolbar button would cost space on the ten pages that cannot use it. Its entry point is `startBatchExport` in `main-actions.ts`, which confirms, begins the Run and posts exactly one message — a declined confirmation must leave no Run behind, because no completion would ever arrive to settle one.
- **The master switch removes the UI; it does not unpatch the scraper.** Turning Cindieh off runs one teardown that removes the toolbar, the badge, the comparer modal, the grid/toolbar filters and the No. Faktur panel, then posts `RESET_SCRAPER` so the still-injected MAIN-world script drops its captured request, filters, invoice row map and running flag. The prototype patches stay installed: they are passive once that state is empty, and re-injecting the script would mean a second interceptor on the same page (ADR-0008). Never describe the switch as "the extension is gone from the page" — say the page's controls are gone and the interceptor is idle.
- **SheetJS is a lazily-imported chunk, never a static import (ADR-0013).** `exporter.ts` reaches it only through `loadXLSX()`, a runtime `import()` of the web-accessible `content/xlsx.js`. The library is ~330KB — 81% of what the content script used to carry — and the content script is injected into every portal page, so inlining it taxed every page load with a parse the user may never need (the CSV path needs no library). Two esbuild passes are required because code splitting needs `format: "esm"` while MV3 content scripts must stay IIFE; the cross-pass import therefore uses a **non-literal** specifier, which is what stops esbuild from inlining it, and is silenced via `logOverride["unsupported-dynamic-import"]`. Keep the builders taking `xlsx` as a parameter rather than closing over it, keep a failed load retryable (the loader drops its cache), and keep the failure visible in the panel. `import type { WorkBook } from "xlsx"` is fine — type-only imports are erased. Importing `xlsx-runtime.ts` from anywhere silently restores the old bundle.
- **A preference the page UI reads must be applied in place, not by re-injecting.** `setExportFormatDefault` only moves the check mark onto the stored format's item inside the export menu, and `setOneClickExport` only reshapes the injected dropdown; calling `injectExportButton` again would fight Angular for the same node, and `removeExportButton` must keep removing the whole `#ch-export-dropdown` container (and clearing `dropdownNodes`). The toolbar's DEFAULT shape is a SINGLE button (`#ch-export-dropdown-btn`, label "Ekspor", click toggles the menu) with the chevron inside it — an always-on split main-button + caret was tried and reverted because it consumed too much room beside the portal's own buttons. The split lives on as the opt-in `oneClickExport` preference: the caret button `#ch-export-dropdown-caret` is built once in BOTH modes but stays `ch-hidden` and chevron-less until the mode moves the chevron into it, so enabling it costs no space for anyone else and switching modes never rebuilds the DOM. Keep the default off. The re-injection the MutationObserver schedules must likewise not rebuild a live toolbar: `resolveToolbarPlacement()` is the ONE anchor resolution (injection and the placement check must not pick different headers — that mismatch is what made the SPT menu slam shut mid-click), a misplaced toolbar is MOVED with `placeInToolbar`, and `menuOpen` hands an open menu to a rebuilt dropdown.
- **The original wiring note, for the world entries:** Extracting patch bodies leaves the IIFE holding only wiring (which prototype goes to which factory, install order, teardown) — that layer is on its own, in both worlds. `scraper-boot.unit.test.ts` imports the real `scraper.ts` over `stubFakeDom()` plus stubbed `window`/`location`/`XMLHttpRequest`/`HTMLAnchorElement` and asserts both ends: every patched reference differs after boot and comes back on `pagehide`. `main-boot.unit.test.ts` does the same for `main.ts` with a deferred `storage.local.get` and a fireable `MutationObserver`: scraper.js is not appended until the read resolves (the scraper resolves its log flag at module load), the page mirror lands before the append, the one-time marker holds across that await, and a failed load clears the marker so injection retries. Extend the matching harness when you add or move a patch rather than trusting the seam suites to cover the plumbing. The two smaller contexts have startup tests of their own — `popup.unit.test.ts` (controls reflect stored state, a change persists rather than just repaints, a write lands under the prefixed key, the debug toggle applies locally, a refused notification permission rolls the switch back, and reset removes exactly the managed keys) and `background.unit.test.ts` (install listener, and the documented cold-start race where the startup log is emitted before the switch is known).
- **Stateful modules** export a production singleton plus a `createX()` factory so tests use independent instances, never shared module state.
- **Tests** live in `src/tests/` with relative imports (`../content/...`): `*.unit.test.ts` for vitest `describe`/`it`/`expect` suites, `*.property.test.ts` for fast-check property tests, `*.invalid.property.test.ts` for rejection cases. Shared browser mocks live in `src/tests/__mocks__/` (e.g. `xhr-mock.ts`). Test discovery runs on vitest's defaults — `vitest.config.ts` extends only the `test` key with coverage settings and never overrides `include`.
- **The microsite may not drift from the code.** `microsite/index.html` and `microsite/privacy.html` restate facts that live in TypeScript — filename prefixes, manifest permissions, shortcuts, the supported page list, the status labels of both result grids, the generated export filenames, every popup control, and the site's own hostname — and nothing in the build fails when one of those moves. `microsite-sync.unit.test.ts` is the backstop: it reads the page from disk and compares it against `export-source.ts`, `manifest.json`, `shortcuts.ts`, `page-context.ts`, `comparer-logic.ts`, `exporter.ts`, `downloader.ts`, `popup/popup.html`, and `src/shared/extension-preferences.ts`. Adding an export source, a permission, a shortcut, a portal page, a status, a filename, or a preference therefore means the page must change in the same commit or the suite goes red. Every fact is searched **inside its own container** — the prefix table, the permission table, the tab panel that owns it (`.status-legend`, the `.filechip` samples), or `.pref-table` — because the page mentions `BP-`, `storage`, `Nama file`, and the status labels in prose too, and a page-wide search would keep passing after the container itself went stale. A second block, `microsite — house style`, guards the design rules themselves rather than a fact about the code: the eyebrow budget (at most one label per three heads, comments stripped first), no em-dash or en-dash in rendered text across all three pages (again comments stripped, JSON-LD deliberately NOT stripped because those answers are rendered by a search engine), and no `font-style:italic` anywhere in the sheet, since none of the five self-hosted faces ships an italic cut. Each was proven with a counterfactual: four extra eyebrows, one planted em-dash in an `<h2>`, and the same em-dash inside a comment (which must stay green). The landing page also has seven sections rather than nine: `#kompatibilitas` and `#roadmap` were each a full 86px-padded section for content the install cards and the download row already carried, and both sat on the same alt-bg band as a neighbour, so folding them in cost no rhythm. Every table on the page carries an `.sr-only` `<caption>` and the settings clusters use `scope="rowgroup"`, and the English UI literals carry `lang="en"` so an Indonesian screen-reader voice does not mispronounce them. Plex Mono **400** is preloaded because the hero eyebrow and the mockup address bar are mono and above the fold; only its 500 and 600 cuts are not. The same suite guards the page's own structure: one label and one panel per feature tab, the `.js` scoping that keeps the scroll-reveal visible without JavaScript, the metric-matched `@font-face` block, the site hostname agreeing across canonical/`og:url`/sitemap/robots, the 404 page keeping its `<base href="/">`, `sitemap.xml` listing every canonical page and nothing else in BOTH directions, and every cross-page link being relative AND resolving to a file that exists (the pages must stay portable to a subdirectory, so a root-anchored `/privacy.html` fails exactly as a dead `beranda.html` does). The privacy page's permissions table is checked against `manifest.json` in BOTH directions, because a store reviewer reads it before installing: every requested permission must be named, and every claimed permission must exist in the manifest. The page list, the popup rows, and the two status legends are also checked in reverse: nothing the page advertises may be unsupported, unrendered, or unproducible by the code. Filename samples are compared as whole chips, never as substrings, because the prefixed sample `PTABC-FPK-072026.xlsx` contains `FPK-072026.xlsx`; a PDF sample that fits is spelled out and must match exactly, and only the long e-Faktur one is abbreviated with a middle ellipsis and matched on its two halves. The same suite computes WCAG 2.1 contrast in the test file itself: 86 rendered text pairs, INCLUDING `404.html`, which carries its own inline `<style>` block — so a rule there is a separate usage, not covered by whatever the landing page does with the same token at 4.5:1 (3:1 large), the literal `rgba()` in `.code-block .cmt`, and the three control borders at 3:1 for WCAG 1.4.11. That exists because the microsite palette is a deliberate byte-for-byte mirror of `styles/injected.css` (`--match`=`--ch-match`, `--diff`=`--ch-diff`, `--bad`=`--ch-bad`, `--miss`=`--ch-text-muted`, `--only-ct`=`--ch-blue`, `--ink-soft`=`--ch-text-dark`, `--card`=`--ch-white`, `--paper`=`--ch-paper`, `--paper-alt`=`--ch-paper-alt`, `--stamp`=`--ch-primary`), and those hues were chosen as FILLS: as text on their own 12-14% tints they measured 2.4:1 to 4.2:1. So text uses a `-ink` twin of each status hue (same hue and saturation, lightness only, solved to 5:1) while every `background:`, border and swatch keeps the base token — the mirror survives intact and the site passes AA. The suite enforces both halves: the ten base tokens must still equal `injected.css`, and no `color:` may name a base status hue instead of its `-ink` twin. `--line-strong` stays a decorative hairline; `.btn-ghost` and `.ct-input` draw `--control-line`, because a control boundary needs 3:1 and a hairline measures 1.75:1. NOTE: `injected.css` carries the SAME rule now: it ships `--ch-match-ink`/`--ch-diff-ink`/`--ch-bad-ink` with the exact values the mirror solves, and the three tint summary/status pills (`summary-ok`, `summary-warn`, `status-error`) paint their text from the `-ink` twin while backgrounds, borders and the already-passing `--ch-info` pill keep the base token (`0c2fc06` — there is no `--ch-info-ink`, because that base hue clears 4.5:1 on its own tint). The ten-token equality check therefore still passes unchanged, and the failure mode to resist is a new `color:` that names a base status hue on that hue's own tint — in either sheet.
- **Coverage has a ratchet, not a goal.** `pnpm test:coverage` runs the v8 provider and enforces global `thresholds` (statements 87.7 / branches 81.3 / functions 83.7 / lines 89.3) that sit just under the measured 88.03/81.71/84.10/89.72, so ordinary churn cannot redden the build while new untested logic does. **Raise them as coverage improves; never lower them to make a red build green.** Two files are excluded on purpose: `scraper-types.ts` compiles to an empty module (types only), and `xlsx-runtime.ts` is the SheetJS build chunk that ADR-0013 forbids tests from importing — its correctness comes from importing the BUILT `content/xlsx.js`, not from unit-testing the source. The known gaps that hold the average down, so a low number reads as known rather than mysterious: `scraper.ts` 39% (the MAIN-world IIFE wiring), `downloader.ts` 44% and `ui-filters.ts` 55% (the PDF filename dispatch and the toolbar filters), `main.ts` 68%, and the panel view modules: `ui-comparer.ts` 90% statements at 56% **branch** and `ui-panel.ts` 74%, both dominated by DOM construction and the overlay's open/close paths rather than by untested decisions — the decisions moved to `checker-logic.ts` (98%), `comparer-logic.ts`, and the fully covered `result-columns.ts`. Splitting the checker tab out (`ui-checker.ts`, 97% with its own render suite) is what closed most of that gap. Statements and lines were held flat through the export-source extraction even though `export-source.ts` is 100% covered: `exporter.ts` shrank 675 → 381 lines, so its still-untested download entry points weigh more heavily against a smaller denominator.
- **Preferences flow one way: schema → guard → cache.** `src/shared/extension-preferences.ts` owns the keys and exactly one normalizer per value; `src/content/preferences.ts` owns storage access and the field-name → storage-key table. Two things follow. A `Partial<ExtensionPreferences>` must never be passed straight to `storage.local.set` — the fields are camelCase and the keys are `cindieh*`, so the raw patch would write keys nothing reads back and the control would look saved while doing nothing; `writePreferences` does the translation. And action paths that cannot await a read (a click deciding to confirm a download) take `getPreferences()`, the synchronous snapshot that `readPreferences()` and the storage listener both keep current. PACING is the exception that proves the rule: the delays are applied in the MAIN world, which cannot reach extension storage, so `page-pacing.ts` mirrors the preset into page storage and `ScraperContext.getPacing()` resolves it per RUN — a change applies to the next export in an open tab with no reload, unlike the debug flag, which is fixed at scraper module load.
- **A popup control that COMMANDS a tab reuses `storage.local`; it does not open a messaging channel.** ADR-0002 deleted the `runtime.onMessage` channel because nothing sent on it. "Bersihkan cache", the completion notification, and the `SHOW_PANEL_REQUEST_KEY` command a clicked toast sends to the content script therefore publish a changed value (a timestamp, so two clicks in a row are still a real change) and the receiving context acts inside its existing `storage.onChanged` listener. A tab that is not open simply misses that click.
- **Pacing may only ever get SLOWER.** RATE_LIMITING.md fixes the code's own inter-request delay as the floor and the portal's page-size caps as `step`. The preset is a multiplier of at least 1 applied to every delay site (paginated loop, bulk PDF, per-invoice lookup) and it never touches `step`; a control that could go faster would be a regression of the project's core compliance claim.
- **A clicked completion toast returns to the run's own page; the panel is opened by a separate storage command.** The published record carries `pageUrl` (the content script's `location.href`), which `announceCompletion` remembers per toast id in a worker-lifetime map — the click listener only receives the id. `focusPortalTab()` queries tabs first by `notificationTabPattern(pageUrl)` (portal origin plus the first two path segments, the SPA-stable section), then by the manifest's portal pattern (which the existing host permission already covers — no `tabs` permission is added), and focuses both the tab and its window; the reason for the toast lives in the panel, so the content script is asked to open it over the same seam as any other background → tab command. The `notifications.onClicked` id must keep the `cindieh-completion-` prefix, which is how an unrelated id is ignored. A toast that outlives the service worker loses its map entry and falls back to any portal tab.
- **`notifications` is an optional permission, requested from the popup on the user's click.** Declaring it up front would make every existing install re-consent to a permission the extension does not need until the switch is turned on. The request is issued with no `await` in front of it (Firefox only honours it while the click's user gesture is live), and a refusal rolls the switch back rather than leaving it promising a notification that cannot be sent.
- **Storage reads are guarded, and the guard sets a definite UI state.** A rejected `storage.local.get`/`set` must not surface as an unhandled rejection or leave a control half-rendered: fall back to the documented default and report through `debugError` (`loadExportModePreference` in `main.ts`, the same guard in `popup.ts`). `writeDebugPreference()` swallows on purpose.
- **Teardown restores each surface independently.** `teardownInterceptors()` runs one guarded restore per patched surface so a single refused assignment (e.g. the portal redefining a prototype method as non-writable after we patched it) cannot strand the others; failures go to `debugError`. Keep new restores in that list, and prove it with a throwing property setter as `scraper-boot.unit.test.ts` does.
- **Strictness:** `tsconfig.json` is `strict`; `eslint.config.js` enforces `@typescript-eslint/recommended` with `no-explicit-any` at warn.
- Section banner comments (`===== NAME =====` / `── ... ──`) mark file and region intent.

## Gotchas

- **Coretax is an Angular SPA** — DOM re-renders constantly. `main.ts` observes mutations and debounces injection (`GRID_FILTER_INJECT_DELAY_MS`) to avoid fighting the framework. Injection logic should respect that pattern.
- **Production logs are opt-in; pick the hook by context.** `debug.ts` logs by default only in dev builds (`NODE_ENV=development`). In a release build the sources win in this order: (1) `?chdebug=1` on the page URL — that page load only; (2) the popup's **Log debug** switch, stored in extension storage and applied by `initDebugFromExtensionStorage()` in the content script, background, and popup; (3) `localStorage.setItem("cindieh:debug","1")` from DevTools, which persists per origin; (4) the build default. Off words (`0`/`false`/`off`/`no`) silence each of them, and a `?chdebug` value is never overturned. Sources 1 and 3 are readable from either world, but **the MAIN-world scraper can only use 1 and 3** — it has no browser API, so extension storage is out of reach there. That gap is bridged rather than left open: the content script calls `initDebugForPageWorld()`, which copies the switch into source 3 and records ownership under `cindieh:debug:ext`, so turning the switch off removes the copy and never the developer's own hand-set value; `injectScraper()` awaits that mirror before appending scraper.js, because the scraper resolves the flag at module load. Sources 1 and 3 are read at module load (reload after changing them); the popup switch takes effect on each context's next startup, applies live in the content script via `storage.onChanged`, and reaches the scraper at its next injection — the read is async, so the first log lines of a cold start may still be suppressed. None of the hooks exposes the bridge token; `enableDebug()`/`disableDebug()` remain for programmatic and test use.
- **Bridge validation is required, not same-page authentication.** Never store the token on `window`, log it, or weaken `shouldProcessPageMessage`. Shared DOM/message exposure means it does not prevent hostile same-page forgery. Removing the script's `src` during initialization reduces DOM exposure without a guaranteed sub-frame lifetime; retain the element/id as the injection marker (ADR-0008).
- **A row's identity is the portal's own id, tested for presence and namespaced** — `getRowDedupeKey` (ADR-0016) reads `RecordId`, then `AggregateIdentifier`, with `undefined`/`null`/`""` as the absent test rather than truthiness, because `0` is a legal id and `||` skipped it. Invoice numbers are deliberately NOT identities: on PPN Masukan the Referensi belongs to the seller and repeats, so keying on it would drop real invoices.
- **Extension-owned XHRs are flagged** `__isCindiehBulk` (see `InterceptedXHR` in `scraper-types.ts`) so the interceptor does not re-capture them and double-fire `DOWNLOAD_PDF_ITEM`. Keep that flag working when adding download paths.
- **Coretax API responses** wrap rows as `{ Payload: { Data: [...] } }`. Parse defensively; the scraper already treats `Payload.Data` as the row array.
- **Dates**: `tax-date.ts` (`formatDate`, `extractYear`, `extractMonth`, `extractYMD`, `formatIsoDateTime`) converts ISO strings to Indonesian `DD/MM/YYYY`; it is timezone-aware, and existing tests pin behaviour across `+07/+08/+09/Z` offsets. Do not "simplify" it, and put new date/period parsing there instead of hand-rolling regexes. `formatIsoDateTime` is deliberately narrower than `formatDate` — it reformats only ISO *datetimes* and leaves a pure `YYYY-MM-DD` alone, because an export column that catches undeclared timestamps must not rewrite a value whose own column already says what it is.
- **Filenames** use per-source prefixes in `PREFIX_MAP` (`FPK-`, `FPM-`, `RET-FPK-`, `A2-`, `B2-`, `PPH21-L1A-`, `BP-`, ...) — exporter specs enumerate all 11 sources.
- **`dist/` is a gitignored build artifact.** Never edit it; the build regenerates it. `build.cjs` rewrites the manifest per browser (Chrome `service_worker`, Firefox scripts + `browser_specific_settings.gecko.data_collection_permissions`), so manifest edits go in the source `manifest.json`.
- **Versioning:** `pnpm version` runs `sync-manifest.cjs` to keep `manifest.json` in sync; releases go through `pnpm release` (release-it + `@release-it/conventional-changelog` → CHANGELOG.md, tag `vX.Y.Z`, no push). The `after:bump` hook in `.release-it.json` runs `sync-manifest.cjs` then `pnpm run release:assets` (chrome build → firefox build → the three archives), and `github.assets` uploads `dist/cindieh-{chrome.zip,firefox.xpi,source.zip}` to the GitHub Release — assets are built after the version bump so the packaged manifest carries the new version, and release-it creates a draft release first precisely because assets need a release to attach to. Needs `GITHUB_TOKEN` with `contents: write`; the tag is not pushed (`git.push: false`), so push it manually. Hooks are skipped entirely in dry-run (`shell.exec` no-ops when `isDryRun`), so `pnpm release:dry-run` still touches nothing. `pnpm run release:assets` builds the archives without publishing. The microsite links to them via the stable `releases/latest/download/<file>` URLs.
- **pnpm 11 auto-runs `pnpm install` before every command** (`verify-deps-before-run`), and the install fails on the ignored `esbuild` build script (`ERR_PNPM_IGNORED_BUILDS`). Run commands with `pnpm --config.verify-deps-before-run=false <cmd>` to skip the pre-run install; the `node_modules` tree stays valid.
- **TypeScript 7 is the compiler; `typescript` is aliased on purpose.** `tsc` runs the Go-native TypeScript 7 (`@typescript/native`), while the `typescript` dependency is deliberately `npm:@typescript/typescript6` because TypeScript 7 ships no compiler API and `typescript-eslint` (peer: `<6.1.0`) needs one. `pnpm exec tsc6` gives the 6.0 compiler. Never bump `typescript` to `^7` directly — lint breaks; keep both aliases in sync when upgrading.

## Validation loop

With `cd` at the repo root:

1. **Typecheck** — run `pnpm typecheck`; criterion: zero TS errors.
2. **Tests** — run `pnpm test`; criterion: the whole vitest suite passes, including new coverage for changed logic. Run `pnpm test:coverage` when you change logic: the ratchet must stay green, and changed logic is expected to move its own module's number up rather than the global average down.
3. **Lint** — run `pnpm lint`; criterion: no eslint errors (warnings acceptable).
4. **Build** — run `pnpm build:chrome` (and `build:firefox` when the change touches cross-browser or manifest concerns); criterion: `dist/cindieh-<browser>/` completes with the manifest produced. For UI changes, nothing substitutes loading `dist/cindieh-chrome` unpacked against the live portal (see below).

## Portal verification (manual)

Unit tests cover the seams, the patches, and the wiring; nothing covers the live portal. Re-run this after any change to the download path (`scraper.ts`, `scraper-pdf.ts`, `scraper-fetch.ts`, `scraper-nets.ts`, `scraper-xhr-patches.ts`, `scraper-xhr.ts`, `downloader.ts`): rebuild, reload the extension, **load the grid once first** — an unpopulated `invoiceRowMap` is what yields `TANPA_REFERENSI` filenames, a missing capture rather than a blocking failure — then record the current download list as the baseline.

Evidence is Network + the download list, not console output: in DevTools → Network (filter `download-invoice-document`, Preserve log) each click must produce **exactly one** request whose response body is the failure payload `{"IsSuccessful":false,"Content":""}`, and `chrome://downloads` must gain **exactly one** file per click, extension-named (`SZ-0447-07-26 - 010.000-26.00000001.pdf` for e-Faktur, `01-2026-BP-001-PT Contoh.pdf` for withholding) — never a portal-named one.

The popup is UI too, so load it once per build and check the same claims its tests pin: each control shows the stored value on open, a change reaches the open portal tab without a reload (the toolbar label follows the default format, the master switch paints and unpaints the whole toolbar), "Bersihkan cache" empties the panel's data so the next export refetches, "Reset preferensi" returns every control to its default while leaving the export mode and the debug switch alone, and the notification switch only goes on after the browser's permission prompt is accepted.

Run all six of the download checks below, because each exercises different code: one 1-click download · two downloads inside the 5s processing window · a legitimate portal save/popup between two blocks (the nets must self-reset, not pile up) · bulk e-Faktur and withholding with the >10-file confirmation both declined and accepted · scrape/export/filter/stop untouched · SPA navigation followed by a full reload (one injection per page, teardown restores every patched surface).

Symptom → suspect: a portal-named PDF with full content means the sabotage never applied (check whether that endpoint went via fetch or XHR); the same file at 0 KB means the dummy stopped being a failure payload; two requests per click means a replayed request or a doubly registered reader; two extension-named files for one row means double emission (`__isCindiehBulk`, XHR arm state); a legitimate download swallowed means the net scope widened; `teardown failed` names one surface and the rest still restore. For logs use `?chdebug=1` (that load only, and it reaches the scraper) or the popup switch (MAIN world from the next page load, since the scraper resolves its flag at module load); confirm the mirror landed by checking `cindieh:debug` + `cindieh:debug:ext` in Application → Local Storage. **Stop and collect evidence the moment a portal-named PDF with real content appears** — that is a regression of the primary block, not a nuance.
