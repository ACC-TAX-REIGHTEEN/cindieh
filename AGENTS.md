# AGENTS.md

## Project

**Cindieh** — a Manifest V3 browser extension (Chrome + Firefox) for the Indonesian DJP Coretax tax portal (`coretaxdjp.pajak.go.id`). It replaces slow portal workflows with one-click features: bulk export of grid data to Excel/CSV, bulk PDF downloads, reference-number search, a comparer that checks internal invoice records (pasted from Excel) against Coretax, and an accuracy checker (Pengecekan) that recomputes each recorded PPN Keluaran row's DPP / DPP Nilai Lain / PPN against a chosen benchmark (Acuan).

Tech: TypeScript (strict), esbuild bundling, SheetJS (`xlsx`), vanilla DOM/CSS — no UI framework. Commands and scripts live in `package.json`; install deps with `pnpm install`.

**Language split:** user-facing strings (UI text, alerts, panel status) and the README are in **Indonesian**; code comments and this file are in English. Keep user-visible text in Indonesian.

**Architecture decisions** live in `docs/adr/` (numbered, one per decision; see `docs/adr/README.md` for the index). The domain glossary is `CONTEXT.md`. When changing the shape of a module, check both before re-litigating a settled seam.

## Two-worlds architecture

The extension runs in two JavaScript worlds on the Coretax page that communicate **only** through token-validated `postMessage`:

- **Isolated world** — `src/content/main.ts`: the content script (has `browser.runtime`). Injects in-page UI, fires browser downloads, relays messages. Workflow UI lives in-page; the manifest also declares an action popup (`popup/popup.html`) that owns every stored preference — master switch, export mode, default file format, filename prefix, pacing, bulk-download confirmation, comparer defaults, debug switch, completion notifications — via `storage.local`, which is its only channel (see Gotchas).
- **MAIN world** — `src/content/scraper.ts`: injected into the page via a `<script>` tag pointing at the web-accessible `content/scraper.js`. It sits next to the portal's own code, so it can intercept XHR/fetch, read request bodies (filters), and **capture** API responses for scraping and PDF download. It has no browser API.

The **bridge token** correlates messages with the current bridge: `bridge.ts` generates it in the isolated world and passes it through the script URL without storing it on `window`. MAIN-world code can still observe it through the shared DOM and `postMessage` traffic; it is not secret authentication against hostile same-page scripts. `shouldProcessPageMessage` checks source, origin, token, and direction. Source/origin bind the window and origin, not the JavaScript world; `FROM_PAGE` and `FROM_CONTENT` are protocol fields, not proof of sender identity. Keep the two-worlds seam and token validation with these accepted limitations (ADR-0007).

Key message types:
- isolated → MAIN: `START_SCRAPE` (carries `skipPdf` when the request is an XLSX/CSV export rather than a bulk PDF download — see `scrapeIntentForFormat`, and `batchMonths` to sweep a whole tax year as ONE Run — see `scrape-batch.ts`/ADR-0018), `STOP_SCRAPE`, `SCRAPE_BY_INVOICES`, `SET_SERVER_FILTER`, `RESET_SCRAPER`, `START_PDF_DOWNLOAD`
- MAIN → isolated: `INJECTED_READY`, `SCRAPE_PROGRESS`, `SCRAPE_COMPLETE` (with `cancelled` it is the report a stopped sweep makes about the masa it finished — ADR-0020), `SCRAPE_ERROR`, `DOWNLOAD_PDF_ITEM`, `SCRAPE_DATA_CHUNK` (one slice of a result too large to clone in one message; the completion's `dataChunks` names how many must arrive, and an incomplete transfer is reported rather than settled — ADR-0017)

`main.ts` and `scraper.ts` each run one `createMessageDispatcher` (from `postmessage-guard.ts`) — a guard-then-dispatch seam per world, keyed by message `type`. New message types register in the handler table of the world that receives them. Run state lives in `run-lifecycle.ts` so the in-page panel survives content-script restarts and SPA navigation. A **Run** spans both worlds (CONTEXT.md): the bridge gives it a `runId`, the Scraper owns its cancellation and identity (ADR-0010), and `run-lifecycle.ts` owns its outcome and debts (ADR-0014). The two halves share no code.

| `scrape-batch.ts` | The REQUEST half of a year-wide export: derive the twelve `TD.007MM` period codes from the value the PORTAL sent (never synthesised — an invented code is a period the portal has never heard of), rebuild the request body's `Filters` array with one entry's `Value` changed, normalise a requested month count, read the captured year for the filename, and measure the filters a grid carries. | `grid-request.ts` | The SHAPE of a Grid request's body (ADR-0041): the `Filters` array every grid request carries, its tolerant reader (`Filters` or `filters`, `PropertyName` or `propertyName`, `Value` or `value`), and the one canonical filter entry both writers build. It also owns the ONE answer to "which filter is the tax period": a filter is found by its WHOLE name (`findFilter`), never by a hint — a name that merely resembles a known one fails UNSAFE (it names the file after a filter the rows never came from), while a name nobody knows fails SAFE (the file takes its period from its rows). `GRID_FILTER_NAMES` is the table of whole names, and a grid's MEASURED name is checked against it, so the sweep's scope and the file's name cannot disagree about the same body. `filtersKeyOf` is the one place that decides which key a body is answered under: a filter written under the key the portal did not send is a filter the portal never receives. Pure: no DOM, no browser API, so the rules are unit tested rather than pinned through four callers |
| `sweep.ts` | What a sweep IS: the PLAN it covers and the counts it gathered (ADR-0040). The plan travels with the counts rather than being rebuilt from them, so a sweep is a plain `{ plan, counts, totalRows }` that crosses the bridge and is stored as plain JSON, and the module answers the two questions its readers actually ask — `missingPeriods(sweep)` (which masa are still missing: the plan minus the ones recorded without an error, so a FAILED masa and one the stop cut short are both resumed) and `isResumable(sweep)` (is there anything left to resume). The derived facts come from the counts rather than travelling beside them: `finishedPeriods`, `failedPeriods`, `emptyPeriods` (a period that vanished between non-empty neighbours) and the row count. `mergeSweeps(previous, incoming, totalRows)` is the union a resume settles (ADR-0023): the incoming counts win for a period they cover again, the plan is the union of the two plans, and the row count is the caller's because the panel names the deduplicated union (ADR-0016). Pure, so the arithmetic is unit-tested rather than discovered on a portal |
| `run-lifecycle.ts` | Everything one Run knows in the isolated world: in flight (`isRunning`), what it owes (`request`/`cancelPending`/`pendingExport`/`noteRequestedInvoices`), what it last produced (`result`), and how it settles (`complete` returns the follow-up work and the missing-invoice shortfall, rejects, or `salvaged` for a stopped sweep whose rows are kept and marked `partialSweep` while everything the Run owed is dropped). One stop door and one required question (ADR-0027): `stop({ keepRows })` ends a Run early for EVERY stop control — the toolbar button, the stop key, the export click that doubles as a stop, a stopped sweep's own report (`salvage` adopts its rows and calls the same function), a failed scrape and a refused completion — and it retires EVERY request the Run carried whatever the flag says and whatever stopped it, so no comparison or check is left for a later, possibly filtered, completion to spend (ADR-0022); the row decision is the caller's, which is the one thing the controls ever disagreed about. `reset()` is a stop that keeps nothing, plus the `freshState()` wipe that makes it forget a resume's union. `begin("sweep-resume")` is the one start whose `stop()` keeps the result: a resume can only ADD to the union a stop salvaged, so ending it early must not take the kept masa with it (ADR-0023). A completion that REPLACES the rows without carrying per-masa counts therefore clears the sweep too — a targeted No. Faktur lookup's filtered subset and a bulk PDF run's own grid scrape are not a year, and stale counts would let the next year-export offer to resume months this world no longer holds. Every retirement also ANNOUNCES itself — `onRetired(kinds)` names the requests it took, in the order the panel runs them, and stays silent when there was nothing to take — because a tab that is still showing "Mohon tunggu, sedang scraping…" cannot see that the completion behind that line is gone (ADR-0026); `cancelPending(kind)` is the one drop that does not announce, since that is a tab retiring its own request. Replaced the ten-field `ContentState` (ADR-0014). No browser or DOM dependency (each announcement is a callback). **A sweep's rows with masa still pending survive the page (ADR-0023 amendment):** `onResumable` announces what a resume would start from after every mutator (`begin`, `stop`, `reset`, `complete`), so `main.ts` writes or clears one snapshot without any stop control remembering to, and `restore(result)` adopts a stored sweep back as a RESULT — never as a Run, so nothing is in flight and nothing is owed. It refuses a result with no masa pending, one with no rows, rows this world already holds, or a Run in flight |
| `sweep-snapshot.ts` | The part of a resumable sweep that outlives its page (ADR-0023 amendment). The SHAPE is pure: `sweepContentOf` (a result with rows, fields, counts, a KNOWN source and a sweep that is NOT complete qualifies — a stop's kept half, and equally a sweep that FINISHED with a masa the portal failed to deliver), `readSnapshot` (version, shape, a 24-hour window and a pending masa, else throw the blob away — a blob with nothing left to fetch is dropped rather than offered), `snapshotAppliesTo` (stored source vs `getPageExportSource()`, so a Keluaran half-year is never offered on Masukan) and `stampSnapshot`. ## Conventions

Existing code follows these patterns — new code should match them:

- **Testability first:** logic extracted from the world-entry scripts is written as pure functions with browser/DOM dependencies injected through context interfaces (`ActionDeps`, `ScraperContext` — whose two named halves are `CaptureContext` and `OrchestrationContext`). Add new flows the same way instead of growing `scraper.ts`/`main.ts`. State that outlives one call belongs in a module with a `createX()` factory and an exported singleton, not in a caller.
- **The world-entry wiring is itself tested.** The popup's own context is the smallest instance: every control is looked up defensively (`byId` returning null is a supported state), so the popup still opens when storage or the markup misbehaves.
- **A stopped year-wide sweep reports what it finished; nothing else about a stop changed (ADR-0020).** The rows already collected are the most expensive thing the app can throw away, so a stopped sweep emits one `cancelled` completion with them — but a stop is NOT a completion: `run-lifecycle` keeps the rows (marked `partialSweep`) and drops everything the Run owed, because a pending comparison spent against eleven of twelve months would look complete. That is the rule for every stop path, not only the sweep's (ADR-0022): the export click that doubles as a stop keeps the rows and drops the requests too, and the reason generalises — the completion that arrives next can be a No. Faktur lookup whose rows are a subset, which a queued comparison would read as "Tidak ditemukan". The report necessarily arrives under the run id the stop retired, so `bridge.isStoppedRunMessage` remembers it and `main.ts` admits exactly one REPORT through that window — the chunk stream the rows travel in (ADR-0017) plus the `SCRAPE_COMPLETE` with `cancelled` that names it, because a big taxpayer's salvage IS chunked and admitting the completion alone would report it as an incomplete transfer; a stale completion from any other run still cannot pose as the current one. No file is ever written by the stop itself, and the one the user can ask for afterwards is named `…-sebagian`. **A tab that was waiting on the stopped request is told too:** every retirement announces the requests it took, and `main.ts` hands each kind to the tab that queued it, so the "Mohon tunggu, sedang scraping…" line is REPLACED by one short reason (`RETIRED_REQUEST_NOTICE`) instead of promising work that can no longer arrive — never left blank, since a blank line reads as "nothing was asked for" — while the badge keeps the stop's own account (ADR-0026). A cancellation that collected nothing keeps the old behaviour and wording, and a stopped plain scrape (not a sweep) still emits nothing. **The salvaged rows are resumable, and that is the same menu entry (ADR-0023).** The kept counts are what says which masa never finished (`sweep.missingPeriods`: the sweep's plan minus every period recorded without an error, so a FAILED masa and one the stop cut short are both resumed), the message asks the MAIN world for exactly those codes plus the year they came from, and the MAIN world narrows them against the plan the PORTAL's own request yields — never a code the portal did not offer, and not at all when the grid's year filter has moved. The union of the two halves is settled in the ISOLATED world, because that is where the kept rows live: `unionRows` (deduplicated by the portal's row identity, previous rows first) plus `sweep.mergeSweeps` (the incoming counts win for a period they cover again), and the panel's row total is the FILE's rows rather than the sum of two accumulators' counts, which can overlap where a failed masa's partial rows were fetched again. A finished resume is a whole year-wide sweep again, so `partialSweep` and its `-sebagian` name stop applying; ending a resume early keeps the union it was adding to. **The plan travels with the counts (ADR-0040):** a sweep is `{ plan, counts, totalRows }`, the plan being the period codes it COVERS, so nothing rebuilds the year from a seed — a rebuild assumes the first count is month 01, and a resumed half starts wherever the resume began. The panel's "10 dari 12 masa" reads `plan.length`, the empty and failed lists are derived from the counts rather than carried beside them, and the two questions four callers used to ask with four guard sets (`missingPeriods`, `isResumable`) are one module's two answers. **The resumable rows also survive a reload, and a FAILED masa is one of them** (ADR-0023 amendment, extended 2026-10-19): `run-lifecycle.onResumable` announces them after every mutator, `main.ts` writes them through `sweep-snapshot.ts`, and boot restores them — a stop's kept half AND the rows of a sweep that FINISHED with a masa the portal failed to deliver, because the one-month retry is the same resume and the stored `partialSweep` only decides whether the file is named `-sebagian`. Both are offered only on the grid they came from, only within a day, only if they fit in storage, and `reset()` (navigation, "Bersihkan cache") still clears them, so a tab that has moved on cannot offer rows from the page it left.
- **A page fact answers ONE question; two features that disagree get two facts (ADR-0021).** `isOutputTaxPage()` used to answer both "may this grid take a Referensi filter?" and "is a Referensi a usable identity for matching here?", and on PPN Masukan those answers differ — so one predicate withheld a working filter and left Pengecekan's hand-back dead there. `page-context.ts` now names them apart: **`hasReferenceFilter()`** (both PPN grids; the filter is a LOOKUP, and several purchases sharing the seller's reference is a fine answer) gates the toolbar box, the grid-column input and the checker's double-click hand-back, while **`referenceIsIdentity()`** (PPN Keluaran only) gates the Comparer's tab. Do not re-merge any of them onto `isOutputTaxPage()`: a grid's NAME (`currentGridLabel`), whose invoice a row carries (`counterpartyIsBuyer`) and whether a reference identifies a row are three questions that happen to share an answer on the two PPN grids. **The checker added the fourth case (ADR-0024), and it is the one where a page-wide coupling goes wrong twice over:** on **Retur PPN Keluaran** `isOutputTaxPage()` is false while the row carries the BUYER, `referenceIsIdentity()` is false while the row still has to be named in the report (its NO RETUR), and the check DOES run there — so `isCheckerPage()` (four grids), `checkerRowIdentity()` (Referensi or NO RETUR), `counterpartyIsBuyer()` (Keluaran and Retur Keluaran) and the overlay's `isPanelPage()` (either tab) are four answers to four questions. A grid added to the year-wide export (`isEfakturPage`, ADR-0019) or to the check must be a deliberate decision for the other, which is why neither delegates to the other. `main-boot.unit.test.ts` was extended to boot both PPN grids, because ui-filters' own cases stub the fact away and could not see which one main.ts asks. **The answers themselves live in ONE row per grid (ADR-0028):** `PANEL_GRIDS` in `page-context.ts` is the only place a grid's name, counterparty side, row identity, tab gates and filter fact exist, and every predicate above is a one-line read of it — so the entry point, both tabs, the checker's columns, the progress line and the popup's copy are reads of the same value rather than five lists that must be edited together. A test walks each projection against its row for all four URLs, `ui-export-dropdown.unit.test.ts` and `microsite-sync.unit.test.ts` derive their per-grid casing (and the names the page must advertise) from that table, and the deliberate disagreements are asserted as data — so adding or renaming a grid is one edit, and a fifth hand-written list is what to reject in review.
- **A Grid request's body is read by ONE module, and a filter is named WHOLE (ADR-0041).** `grid-request.ts` owns the body's shape: the `Filters` array, its tolerant reader (`Filters` or `filters`, `PropertyName` or `propertyName`, `Value` or `value`), the one canonical filter entry, and `filtersKeyOf` — the one place that decides which key a body is answered under, because a filter written under the key the portal did not send is a filter the portal never receives (for a period: the same month requested twelve times). **The load-bearing rule is the WHOLE name.** The sweep's SCOPE finds the tax period by its measured name (`MEASURED_SWEEP_FILTERS`); the FILE's NAME used to find it by a HINT — the first filter whose lowercased name CONTAINS "period" or "masa" — so a body carrying `TaxInvoicePeriodStatus` before `TaxInvoicePeriod` named the file after the status while the rows came from the period. That was the name-hint door ADR-0019 closed for the scope and left open for the name; it is now closed on both sides, and `GRID_FILTER_NAMES` is the table of whole names the file is read from, with a test asserting a grid's MEASURED name is among them so the two answers cannot drift apart. **A name that merely RESEMBLES a known one fails UNSAFE — it names the file after a filter the rows never came from — while a name nobody knows fails SAFE, because the file then takes its period from the rows it holds.** So the table is whole names and the substring match is gone; do not reintroduce a `name.includes(...)` filter lookup, and do not add a grid's filter name to a table without the measurement that justifies it (the measured table itself is unchanged, and the other three e-Faktur grids still refuse the year-wide export).
- **A scraped row is named ONCE, and it is the name its file carries (ADR-0042).** A bulk-download row is named twice — in the panel's progress line and failure list, and in the file the download lands as — and the download ORDER is the only thing that ties a failure back to a row once the run is over, so the two have to be the same row. `row-name.ts` owns the ladder: per export source, the fields that NAME a row (its Referensi, its return number, its slip number) and the fields that carry the INVOICE number it belongs to. The panel's LABEL is the first of `name` then `invoice` the row carries, and the file's two slots come from the same two lists — so a failure report and the file it names cannot disagree about which row failed. **Three rows used to be named two ways at once:** a retur carrying both a Referensi and a return number (reported as the Referensi, filed as the return number), a Bukti Potong carrying only the SINGULAR slip number (reported as "BP-001", filed as "TANPA_NOMOR"), and an e-faktur row carrying a TaxInvoiceNumber and a LetterNumber (reported as the TaxInvoiceNumber, filed as the LetterNumber). The Bukti Potong's two spellings are ONE list, read by the ladder and by the exported column alike, so a slip's spelling cannot be spelled differently in two places. The file keeps its own SHAPE (`Reference - LetterNumber.pdf`, `MM-YYYY-Nomor-Nama.pdf`, the generic `SOURCE-name.pdf`) and the placeholders a filename needs when a part is missing — those are file conventions, not row facts.
- **A feature that only some pages can use belongs in those pages' menu, not in the toolbar.** The year-wide export adds one item to the export dropdown, built on the four e-Faktur PPN grids (`isEfakturPage()` — Keluaran, Masukan, both Retur), because a toolbar button would cost space on the seven pages that cannot use it. Its entry point is `startBatchExport` in `main-actions.ts`, which confirms, begins the Run and posts exactly one message — a declined confirmation must leave no Run behind, because no completion would ever arrive to settle one. The gate and the sweep's own scope guard are two different doors: the gate decides where the item is offered, `batchScopeError` decides whether the request it captured can be swept at all.
- **The master switch removes the UI; it does not unpatch the scraper.** Turning Cindieh off runs one teardown that removes every surface — the toolbar, the badge, the panel overlay, the grid/toolbar filters and the No. Faktur filter — and then posts `RESET_SCRAPER` so the still-injected MAIN-world script drops its captured request, filters, invoice row map and running flag. The prototype patches stay installed: they are passive once that state is empty, and re-injecting the script would mean a second interceptor on the same page (ADR-0008). Never describe the switch as "the extension is gone from the page" — say the page's controls are gone and the interceptor is idle. **Each surface is removed by the module that built it** (ADR-0033), so the teardown is a registry call and not a list of ids somebody has to remember: a hand-written id list had already leaked the toolbar filter's container and left the page `inert` behind an open panel. A surface's removal may undo more than it deletes — the panel is CLOSED before it goes, which is what hands the background back from `inert`.
- **SheetJS is a lazily-imported chunk, never a static import (ADR-0013).** `exporter.ts` reaches it only through `loadXLSX()`, a runtime `import()` of the web-accessible `content/xlsx.js`. The library is ~330KB — 81% of what the content script used to carry — and the content script is injected into every portal page, so inlining it taxed every page load with a parse the user may never need (the CSV path needs no library). Two esbuild passes are required because code splitting needs `format: "esm"` while MV3 content scripts must stay IIFE; the cross-pass import therefore uses a **non-literal** specifier, which is what stops esbuild from inlining it, and is silenced via `logOverride["unsupported-dynamic-import"]`. Keep the builders taking `xlsx` as a parameter rather than closing over it, keep a failed load retryable (the loader drops its cache), and keep the failure visible in the panel. `import type { WorkBook } from "xlsx"` is fine — type-only imports are erased. Importing `xlsx-runtime.ts` from anywhere silently restores the old bundle.
- **A preference the page UI reads must be applied in place, not by re-injecting.** `setExportFormatDefault` only moves the check mark onto the stored format's item inside the export menu, and `setOneClickExport` only reshapes the injected dropdown; calling `injectExportButton` again would fight Angular for the same node, and `removeExportButton` must keep removing the whole `#ch-export-dropdown` container (and clearing `dropdownNodes`). The toolbar's DEFAULT shape is a SINGLE button (`#ch-export-dropdown-btn`, label "Ekspor", click toggles the menu) with the chevron inside it — an always-on split main-button + caret was tried and reverted because it consumed too much room beside the portal's own buttons. The split lives on as the opt-in `oneClickExport` preference: the caret button `#ch-export-dropdown-caret` is built once in BOTH modes but stays `ch-hidden` and chevron-less until the mode moves the chevron into it, so enabling it costs no space for anyone else and switching modes never rebuilds the DOM. Keep the default off. The re-injection the MutationObserver schedules must likewise not rebuild a live toolbar: `resolveToolbarPlacement()` is the ONE anchor resolution (injection and the placement check must not pick different headers — that mismatch is what made the SPT menu slam shut mid-click), a misplaced toolbar is MOVED with `placeInToolbar`, and `menuOpen` hands an open menu to a rebuilt dropdown.

- **Preferences flow one way: schema → guard → cache.** `src/shared/extension-preferences.ts` owns the keys and exactly one normalizer per value, and they are ONE row per preference (`PREFERENCE_FIELDS`, ADR-0037); `src/content/preferences.ts` owns storage access and PROJECTS the field-name → storage-key table from that same row, so `normalizePreferences` and `preferencesFromChanges` are one loop each rather than a map to keep in step. - **Pacing may only ever get SLOWER.** RATE_LIMITING.md fixes the code's own inter-request delay as the floor and the portal's page-size caps as `step`. - **A loop that walks items belongs to `per-item.ts` (ADR-0034).** The MAIN world's four item flows — the grid's pages, the withholding slips, the e-Faktur rows, the targeted invoice lookup — are ADAPTERS of one loop, not four loops: `runItems(flow, deps)` owns the stop check, the progress line, the breaker, the retry and the wait, and a flow says what one item MEANS. Do not write a new `for` loop over items in the MAIN world; write an adapter. Three rules the module owns, so a new adapter cannot get them wrong: a STOP is not a FAILURE (a stop ends the run and records nothing; a failure is named and counted against the breaker), a result that arrives after a stop is DROPPED rather than taken, and the retry is a DECLARED `ItemRetry` rather than a branch in the body. The one thing a flow still decides is what giving up looks like: the grid's paginated scrape THROWS (its orchestrator turns the throw into SCRAPE_ERROR) while the two PDF loops and the targeted lookup ANNOUNCE the end and return — because those are different kinds of run. The PDF failure sentence is written ONCE (`pdfDownloadFailures()`); it was two verbatim copies before, which is what a shared loop is for.
- **A seam belongs BELOW its users, and the import graph is guarded (ADR-0035).** The MAIN world's context used to live in `scraper-actions.ts`, so the modules extracted beneath it (`period-sweep.ts`, `scraper-intercept.ts`, `scraper-xhr.ts`) had to import their parent to reach it — two real cycles, one of them a VALUE cycle (`abortError`) that the type checker accepts and that only breaks in the bundler's emission order. The seam now lives in `scraper-context.ts`, below every user, and the same rule fixed the isolated world's `result-columns.ts` ↔ `comparer-export.ts` pair. **Do not import a module's parent to reach a type or a helper it happens to own: move the shared thing down, or the dependency is a loop.** `src/tests/content-imports.unit.test.ts` reads `src/content` from disk and fails the build on any runtime cycle, on a cycle inside the MAIN world's closure (type-only edges counted), on a browser API inside the MAIN world (the page script has none — the two worlds talk through `postMessage`), and on an isolated-world module reachable from the MAIN world. If that suite names a cycle, the fix is to move the shared thing DOWN a level, not to break the edge with a lazy import.

A toast that outlives the service worker loses its map entry and falls back to any portal tab.

Keep new restores in that list, and prove it with a throwing property setter as `scraper-boot.unit.test.ts` does.

## Gotchas

- **Coretax is an Angular SPA** — DOM re-renders constantly. `main.ts` observes mutations and debounces injection (`GRID_FILTER_INJECT_DELAY_MS`) to avoid fighting the framework. Injection logic should respect that pattern.
- **Production logs are opt-in; pick the hook by context.** `debug.ts` logs by default only in dev builds (`NODE_ENV=development`). In a release build the sources win in this order: (1) `?chdebug=1` on the page URL — that page load only; (2) the popup's **Log debug** switch, stored in extension storage and applied by `initDebugFromExtensionStorage()` in the content script, background, and popup; (3) `localStorage.setItem("cindieh:debug","1")` from DevTools, which persists per origin; (4) the build default. Off words (`0`/`false`/`off`/`no`) silence each of them, and a `?chdebug` value is never overturned. Sources 1 and 3 are readable from either world, but **the MAIN-world scraper can only use 1 and 3** — it has no browser API, so extension storage is out of reach there. That gap is bridged rather than left open: the content script calls `initDebugForPageWorld()`, which copies the switch into source 3 and records ownership under `cindieh:debug:ext`, so turning the switch off removes the copy and never the developer's own hand-set value; `injectScraper()` awaits that mirror before appending scraper.js, because the scraper resolves the flag at module load. Sources 1 and 3 are read at module load (reload after changing them); the popup switch takes effect on each context's next startup, applies live in the content script via `storage.onChanged`, and reaches the scraper at its next injection — the read is async, so the first log lines of a cold start may still be suppressed. None of the hooks exposes the bridge token; `enableDebug()`/`disableDebug()` remain for programmatic and test use.
- **Bridge validation is required, not same-page authentication.** Never store the token on `window`, log it, or weaken `shouldProcessPageMessage`. Shared DOM/message exposure means it does not prevent hostile same-page forgery. Removing the script's `src` during initialization reduces DOM exposure without a guaranteed sub-frame lifetime; retain the element/id as the injection marker (ADR-0008).
- **A row's identity is the portal's own id, tested for presence and namespaced** — `getRowDedupeKey` (ADR-0016) reads `RecordId`, then `AggregateIdentifier`, with `undefined`/`null`/`""` as the absent test rather than truthiness, because `0` is a legal id and `||` skipped it. Invoice numbers are deliberately NOT identities: on PPN Masukan the Referensi belongs to the seller and repeats, so keying on it would drop real invoices.
- **Extension-owned XHRs are flagged** `__isCindiehBulk` (see `InterceptedXHR` in `scraper-types.ts`) so the interceptor does not re-capture them and double-fire `DOWNLOAD_PDF_ITEM`. Keep that flag working when adding download paths.
- **Coretax API responses** wrap rows as `{ Payload: { Data: [...] } }`. Parse defensively; the scraper already treats `Payload.Data` as the row array.
- **Dates**: `tax-date.ts` (`formatDate`, `extractYear`, `extractMonth`, `extractYMD`, `formatIsoDateTime`) converts ISO strings to Indonesian `DD/MM/YYYY`; it is timezone-aware, and existing tests pin behaviour across `+07/+08/+09/Z` offsets. It also owns how a masa is NAMED in a file: `formatPeriod` turns one period value into the `MMYYYY` label (or leaves a non-period value for the filename rule to recognise by shape) and `extractPeriods` walks a row set's period fields down to the source's own date columns — `exporter.ts`'s filename ladder reads both instead of regexing periods itself. Do not "simplify" it, and put new date/period parsing there instead of hand-rolling regexes. `formatIsoDateTime` is deliberately narrower than `formatDate` — it reformats only ISO *datetimes* and leaves a pure `YYYY-MM-DD` alone, because an export column that catches undeclared timestamps must not rewrite a value whose own column already says what it is.
- **Filenames** use per-source prefixes declared once per export source in `export-source.ts` (`FPK-`, `FPM-`, `RET-FPK-`, `A2-`, `B2-`, `PPH21-L1A-`, `BP-`, ...) — the table is `Record<ExportSource, …>`, so all 11 sources carry their own prefix. The old `PREFIX_MAP` was deleted by ADR-0015 (it had a `default` key, and a default prefix is how a source silently got PPN Keluaran's filename): do not reintroduce it.
- **`dist/` is a gitignored build artifact.** Never edit it; the build regenerates it. `build.cjs` rewrites the manifest per browser (Chrome `service_worker`, Firefox scripts + `browser_specific_settings.gecko.data_collection_permissions`), so manifest edits go in the source `manifest.json`.
- **Versioning:** `pnpm version` runs `sync-manifest.cjs` to keep `manifest.json` in sync; releases go through `pnpm release` (release-it + `@release-it/conventional-changelog` → CHANGELOG.md, tag `vX.Y.Z`, no push). The `after:bump` hook in `.release-it.json` runs `sync-manifest.cjs` then `pnpm run release:assets` (chrome build → firefox build → the three archives), and `github.assets` uploads `dist/cindieh-{chrome.zip,firefox.xpi,source.zip}` to the GitHub Release — assets are built after the version bump so the packaged manifest carries the new version, and release-it creates a draft release first precisely because assets need a release to attach to. Needs `GITHUB_TOKEN` with `contents: write`; the tag is not pushed (`git.push: false`), so push it manually. Hooks are skipped entirely in dry-run (`shell.exec` no-ops when `isDryRun`), so `pnpm release:dry-run` still touches nothing. `pnpm run release:assets` builds the archives without publishing. The microsite links to them via the stable `releases/latest/download/<file>` URLs.
- **pnpm 11 auto-runs `pnpm install` before every command** (`verify-deps-before-run`), and the install fails on the ignored `esbuild` build script (`ERR_PNPM_IGNORED_BUILDS`). Run commands with `pnpm --config.verify-deps-before-run=false <cmd>` to skip the pre-run install; the `node_modules` tree stays valid.
- **TypeScript 7 is the compiler; `typescript` is aliased on purpose.** `tsc` runs the Go-native TypeScript 7 (`@typescript/native`), while the `typescript` dependency is deliberately `npm:@typescript/typescript6` because TypeScript 7 ships no compiler API and `typescript-eslint` (peer: `<6.1.0`) needs one. `pnpm exec tsc6` gives the 6.0 compiler. Never bump `typescript` to `^7` directly — lint breaks; keep both aliases in sync when upgrading.

## Validation loop

With `cd` at the repo root:

1. **Typecheck** — run `pnpm typecheck`; criterion: zero TS errors.
2. **Tests** — run `pnpm test`; criterion: the whole vitest suite passes, including new coverage for changed logic. Run `pnpm test:coverage` when you change logic: the ratchet must stay green, and changed logic is expected to move its own module's number up rather than the global average down.
3. **Lint** — run `pnpm lint`; criterion: no eslint errors (warnings acceptable).
4. **Build** — run `pnpm build:chrome` (and `build:firefox` when the change touches cross-browser or manifest concerns); criterion: `dist/cindieh-<browser>/` completes with the manifest produced. For UI changes, nothing substitutes loading `dist/cindieh-chrome` unpacked against the live portal (see below).

## Portal verification (manual)

Unit tests cover the seams, the patches, and the wiring; nothing covers the live portal. Re-run this after any change to the download path (`scraper.ts`, `scraper-pdf.ts`, `scraper-fetch.ts`, `scraper-nets.ts`, `scraper-xhr-patches.ts`, `scraper-xhr.ts`, `downloader.ts`): rebuild, reload the extension, **load the grid once first** — an unpopulated `invoiceRowMap` is what yields `TANPA_REFERENSI` filenames, a missing capture rather than a blocking failure — then record the current download list as the baseline.

Evidence is Network + the download list, not console output: in DevTools → Network (filter `download-invoice-document`, Preserve log) each click must produce **exactly one** request whose response body is the failure payload `{"IsSuccessful":false,"Content":""}`, and `chrome://downloads` must gain **exactly one** file per click, extension-named (`SZ-0447-07-26 - 010.000-26.00000001.pdf` for e-Faktur, `01-2026-BP-001-PT Contoh.pdf` for withholding) — never a portal-named one.

The popup is UI too, so load it once per build and check the same claims its tests pin: each control shows the stored value on open, a change reaches the open portal tab without a reload (the toolbar label follows the default format, the master switch paints and unpaints the whole toolbar), "Bersihkan cache" empties the panel's data so the next export refetches, "Reset preferensi" returns every control to its default while leaving the export mode and the debug switch alone, and the notification switch only goes on after the browser's permission prompt is accepted.

Run all six of the download checks below, because each exercises different code: one 1-click download · two downloads inside the 5s processing window · a legitimate portal save/popup between two blocks (the nets must self-reset, not pile up) · bulk e-Faktur and withholding with the >10-file confirmation both declined and accepted · scrape/export/filter/stop untouched · SPA navigation followed by a full reload (one injection per page, teardown restores every patched surface).

A stopped sweep is checked the same way, on the live portal (ADR-0020): start a year export, stop it after two or three masa, and confirm the panel names the masa that finished and the rows kept, that no export ran by itself, and that exporting afterwards writes `…-sebagian` into the name. A stop with nothing collected keeps the older behaviour — the plain cancellation line and no data. Then RESUME it from the same menu entry (ADR-0023): the confirmation must name how many masa are kept and how many will be fetched, the Network tab must show only the missing masa being requested, the panel must end on one whole-year report, and the file that lands must carry no `-sebagian` and no duplicated row. Stop a resume once too: the union it was adding to must survive, with the remaining masa named.

The year-wide export's two filters are the one thing the portal still owns: a grid sweeps only if its filter names have been measured into `MEASURED_SWEEP_FILTERS` (ADR-0019), which today is PPN Keluaran and PPN Masukan — the two Retur grids refuse the sweep outright until their rows are recorded, and that refusal is the feature working, not a bug to widen. Measure a grid before expecting it to sweep: on that grid pick one masa and search, then run `tools/masa-batch-diagnostic.js` and `__cindiehMasaDiag.jalankan([1])` (or `verdictFilter()`) — it prints the grid's measured row (or that it has none), the period and year filters the request carries, the guard's verdict, and the row for the per-grid table in `tools/README.md`. A real sweep logs the same reading (`Sweep filters on <source>: …`, `?chdebug=1`). Record the row in `tools/README.md`, ADR-0019 and `MEASURED_SWEEP_FILTERS` together, with a test per grid.

The Referensi filter is UI too (ADR-0021): on **PPN Masukan** both the toolbar box and the column filter in the grid header must appear — a reference lookup there is a supported feature, not a fallback — and a double-clicked Pengecekan row must run a search; on a Retur grid neither appears. Type an empty-prefix search on Masukan once to confirm the panel reports several rows sharing a seller's reference rather than treating it as a failure.

Pengecekan is UI too, and it now covers the retur grids (ADR-0024): on **Retur PPN Keluaran** and **Retur PPN Masukan** the panel key must open it with NO Komparator tab, the first column must read **No Retur** over **Tanggal Retur** (not Referensi), the counterparty column must read **Nama Pembeli** on Retur Keluaran and **Nama Penjual** on Retur Masukan, the exported sheet must repeat those headers, and a double-click must do nothing — there is no Referensi filter to search into, while the invoice grids keep theirs. The panel's toolbar entry point is checked in the same pass (ADR-0025): it must be present on all four grids and named for the tab its page can serve — **Bandingkan data penjualan** with the list icon on PPN Keluaran, **Pengecekan keakuratan nilai** with the check icon on PPN Masukan and both Retur grids — and each one must open straight into the tab it names. The waiting line is checked the same way (ADR-0026): paste rows, click **Periksa** with no grid data yet — the tab says the grid is being fetched — then stop the run (the toolbar stop, or an export click) and the line must go blank while the pasted rows stay; a comparison or check that already ran keeps its summary.

Symptom → suspect: a portal-named PDF with full content means the sabotage never applied (check whether that endpoint went via fetch or XHR); the same file at 0 KB means the dummy stopped being a failure payload; two requests per click means a replayed request or a doubly registered reader; two extension-named files for one row means double emission (`__isCindiehBulk`, XHR arm state); a legitimate download swallowed means the net scope widened; `teardown failed` names one surface and the rest still restore. For logs use `?chdebug=1` (that load only, and it reaches the scraper) or the popup switch (MAIN world from the next page load, since the scraper resolves its flag at module load); confirm the mirror landed by checking `cindieh:debug` + `cindieh:debug:ext` in Application → Local Storage. **Stop and collect evidence the moment a portal-named PDF with real content appears** — that is a regression of the primary block, not a nuance.
